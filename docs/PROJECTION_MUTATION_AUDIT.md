## 1. Findings

1. **`graph/pending/evidence` are publication invalidation counters, not a complete source version.** A new snapshot accepted by `Service.Commit` is readable without changing any of these counters. Promotion of an already-stored stash snapshot is different: a changed stored image explicitly increments `graph`.
2. **A transactional metadata journal already exists in PostgreSQL.** `repository_catalog_state` and `repository_catalog_changes` capture snapshot/ref/history/protocol images, including staged snapshots and snapshot memory-pointer changes. Their UUID `epoch` plus transactional `head_seq` must not be confused with either `RepositoryRevision` or the design's proposed all-dependency source epoch.
3. **Neither existing version mechanism covers all read dependencies.** The catalog omits pending, unsync, session archives, reflog, Git/PR evidence and contribution ledgers, memory/blob ownership, default branch/origin, and access-policy changes. Application counters cover many of those writes, but do not provide their after-images or identify which records changed.
4. **Revision scopes cross read-model boundaries.** Ref/join publication can delete pending pointers with only `graph` changing; archiving a session changes On Hold with only `graph` changing; pending replacement can delete a snapshot/document with only `pending` changing; contribution publication can alter graph/context/memory semantics with only `evidence` changing.
5. **PostgreSQL and FS have different guarantees.** PostgreSQL application writes join one repository transaction; FS writes and `view-revision.json` are separate operations. FS recovery journals do not make all repository mutations and their revision one ACID unit.

Keep the current coherent-input graph fingerprint until dependency coverage is proven. The fingerprint is a safeguard for the inputs it actually hashes, not a substitute for tracking external evidence or checking current access.

## 2. Existing version and transaction contracts

### Application counters

Sources: [application transaction wrapper](../backend/internal/app/transaction.go), [command wrappers](../backend/internal/app/transaction_operations.go), [revision type](../backend/internal/domain/repository_revision.go), [PostgreSQL revision store](../backend/internal/adapters/store/postgres_repository_revision.go), [FS revision store](../backend/internal/adapters/store/fs_repository_revision.go).

| Notation | Actual successful-write behavior |
| --- | --- |
| `G` | `revisionWrite` with the default scope or `"graph"` calls `AdvanceRepositoryRevision(..., false)`: `graph += 1`, not `pending` or `evidence`. |
| `P` | `pendingWriteContext` calls `AdvanceRepositoryRevision(..., true)`: `pending += 1` only. |
| `E` | `evidenceWriteContext` calls `AdvanceEvidenceRevision`: `evidence += 1` only on both audited adapters. A different adapter lacking `EvidenceRevisions` falls back to the graph increment if it supports `RepositoryRevisions`. |
| `none` | Explicit `revisionScopeKey = "none"`, a direct store call, or a separate identity transaction does not automatically increment any of `G/P/E`. Explicit inner `revisionWrite` calls still apply. |
| `C` | A changed, catalog-covered PostgreSQL image advances `repository_catalog_state.head_seq` once per top-level transaction; further covered changes in that transaction reuse the sequence. This is separate from `G/P/E`. No FS equivalent is implemented. |

`repositoryWrite` authorizes and checks document identity before running its callback. With PostgreSQL, only the outer application wrapper automatically advances a revision; nested wrappers identified by `afterCommitKey` do not. Explicit inner `revisionWrite` calls are not coalesced. Without `RepositoryTransactions`, each successful wrapper independently increments its selected counter. For example, the nested `PromoteSnapshotMessage` wrappers can increment FS `G` twice, versus once in a PostgreSQL application transaction.

Most wrappers increment on **successful return**, not on a measured change. An already-up-to-date ref, repeated memory attachment, repeated archive request, or pending compare-and-delete returning a non-error negative result can still increment. Therefore neither counter deltas nor their sum count business facts, mutations, or commits. `Commit` can explicitly increment `G` once for each changed existing snapshot in its batch.

[PostgreSQL `WithinRepository`](../backend/internal/adapters/store/postgres_transaction.go) uses a read-committed transaction, shared identity-access advisory lock, repository graph advisory lock, and repository policy-row lock. Bound adapter calls use the same connection; inner `Begin` operations are savepoints. A read uses a repeatable-read, read-only snapshot. Merely calling `WithinRepository` does **not** call `revisionWrite`. Application failures roll back source rows, automatic counters, catalog changes, and transactional jobs together; ambiguous COMMIT acknowledgement is not blindly retried by the wrapper.

FS does not implement this repository-transaction port. Snapshot/ref/pending locks, atomic file replacement, and join/history recovery journals have narrower scopes. A failed later step or failed revision-file write can leave earlier files changed; exact PostgreSQL counter-count and rollback assertions must not be copied to FS.

### Existing PostgreSQL catalog: useful but partial

Sources: [0074 catalog changes](../schemas/db/migrations/0074_catalog_changes.sql), [0076 snapshot identity images](../schemas/db/migrations/0076_snapshot_doc_identity.sql), [metadata generation reader](../backend/internal/adapters/store/postgres_metadata_generation.go), [admission snapshot reuse](../backend/internal/app/git_admission_snapshot.go).

- Triggers cover INSERT/UPDATE/DELETE on `snapshots`, `refs`, and `context_history`; the `repos` trigger captures INSERT/UPDATE of the projected protocol image. The repo image contains `context_protocol`, **not** its other columns. Snapshot images include `memory_hash`, graft metadata, and, for nonlegacy snapshots, `doc_identity`.
- `cxt_record_catalog` updates a repository row transactionally, using `writer_xid` only to coalesce writes. It does not infer commit order from a global sequence or timestamp. Same-key changes in the same transaction retain the final image/tombstone, not every intermediate action.
- A no-op projected image does not advance `C`. With triggers enabled, direct adapter calls and ordinary SQL against covered tables also advance `C`, even when `G/P/E` do not change.
- Catalog rows are metadata synchronization images, explicitly **not blob-availability receipts**. Catalog coverage alone cannot certify document current bytes, memory contents, ownership, or a complete graph/effective-memory generation.
- `ReadRepositoryMetadataGeneration` exposes `(repo, epoch, sequence)`. Admission reuse already checks this generation, origin, `graph`, and `evidence` together; the complete graph cache does not use it as a universal version.
- Existing `cxt_reset_catalog` rotates the UUID and reseeds current metadata; `cxt_prune_catalog` preserves floor anchors and expires older deltas. Source TRUNCATE is rejected. These are existing maintenance boundaries, not an authorization to run them during this audit.

## 6. Known gaps and boundaries

### Confirmed coverage gaps

- **Visible staging without notification:** a newly inserted snapshot changes full repository/graph inputs while `G/P/E` stays unchanged. Catalog `C` does see it. Existing tests deliberately encode both behaviors. Removing the fingerprint or treating revision notices as complete would change correctness, not merely performance.
- **Catalog is not the complete projection dependency set:** `pending_contexts`, `unsync_contexts`, `session_archives`, standalone `reflog` changes, contribution/evidence tables, legacy memory metadata and blob grants are outside its triggers. Changes to existing repo `default_branch`, `git_remote_url`, `repository_id`, `protect_default`, and `required_doc_identity` are outside the protocol after-image. Some are covered by application `G/E`, others are not.
- **Cross-scope invalidation is required:** `P` alone cannot invalidate On Hold, `G` alone cannot invalidate complete graph/context/effective-memory facts, and `C` alone cannot supply either. Classify effects rather than assuming the counter's name matches one consumer.
- **No changed-record feed in `G/P/E`:** generic wrappers may over-invalidate on no-op/job-status writes; counters carry neither after-images nor tombstones. `C` supplies these only for its covered images and coalesces intra-transaction intermediate states. It cannot reconstruct evidence/pending/archive state at an old counter tuple.
- **Deletion is an input mutation:** pending GC can delete metadata and doc ownership under `P`. Future incremental consumers need removal handling, not just insert/upsert events. Current GC guards preserve referenced/shared documents, archived sessions, attached or legacy memory, divergent captures, and captures without a verified prefix successor; these guards are part of the acceptance contract.
- **Origin fill is unversioned by both mechanisms on an existing repo:** `EnsureRepo` uses `none`, while the catalog repo image includes only protocol. Graph/branch caches currently include origin separately. That protection does not wake revision subscribers.
- **FS publication/counter atomicity is absent:** a complete-looking `view-revision.json` value cannot prove all files correspond to that point. Nested wrappers can overcount, and recovery/partial failures can mutate files without the corresponding counter. PostgreSQL transaction tests do not close this gap.

### Deliberate exclusions and unresolved implementation obligations

- Chunk upload, unselected memory-body persistence, queue claim/lease renewal, and derived-index rebuild are not by themselves new graph/contribution facts. They still need lifecycle/ownership/fence handling if another model consumes their state. An audit must not fix counter gaps by bumping graph on every uploaded chunk.
- `PutPending` accepts activity metadata through the same `P` path as capture changes. No separate application revision distinguishes heartbeat-only from capture changes. The full graph cache includes `P` and the view fingerprint; branch-fact caching can avoid some work, but this is not an independent heartbeat projection.
- Evidence is read outside the view fingerprint. All supported evidence publications must retain their `E`/authorization/fence discipline; a direct evidence adapter/SQL write cannot be assumed safe because the graph still hashes snapshots.
- Session archive records, branch archive facts, immutable memory archives, and repository read-only archive policy are **four distinct operations**. They must remain distinct in an effect classifier and tests.
- The design's all-dependency source epoch, projection generations, and delivery records are not implemented by this document. Whether to extend an existing mechanism is an implementation decision; this audit neither invents a second schema nor declares the existing catalog sufficient.
- Authorization, identity requirements, repository/blob ownership, and strict current-byte integrity must be checked through their existing authoritative paths. A projection watermark is not an access grant or proof that unselected document chunks are healthy.

These gaps constrain a future revision-only cache or durable projection cutover. They do **not** require pausing D2 request-local header reuse that leaves the current publication/version and integrity contracts intact.
